# PoC 計画: RedAmon（AI ペネトレーションテスト）の使い勝手検証

## 目的

OSS の AI レッドチームフレームワーク **RedAmon** の**使い勝手・導入コスト・検出精度**を検証し、**現場（QA）に「ペネトレーションテスト自動化をどう取り込めるか」を共有する**ための素材を作る。

- きっかけは不正アクセスのインシデント。「攻撃側の視点でアプリを診断する」仕組みを QA に取り込めるかを見極める。
- このフェーズで確かめるのは **ツールの評価**であって、特定アプリの脆弱性診断そのものではない。
- 本命は RedAmon。AI プロダクト向けの LLM セキュリティ評価（promptfoo）は別計画 `poc/promptfoo/` で扱う。

## 安全境界（最重要・先に固定する）

RedAmon は**実際に攻撃を行い、修正 PR も自動生成する**ツール。対象を誤ると法に触れる。

| 区分 | 内容 |
| --- | --- |
| ✅ 対象にしてよい | 自分が管理する**ローカル Docker の練習用脆弱アプリ**。自分のローカルで立てた couple-gifted（Rails） |
| ❌ 対象にしない | 勤務先の本番・ステージング、ホスティング事業者上の実システム、他社・第三者のサーバー、クラウド上の実環境 |

- 実システムへの診断は、**書面での許可とスコープ合意**を取った別フェーズでのみ行う（許可なき攻撃は不正アクセス禁止法に触れる）。
- RedAmon 用の GitHub トークンは、この POC 用に**権限を最小限**に絞る（修正 PR 機能を試す場合も POC 用リポジトリ限定）。
- RedAmon 自体のガードレール（攻撃対象の制限など）の挙動も、評価項目として記録する。

## 対象環境

| # | 対象 | 位置づけ | 備考 |
| - | ---- | -------- | ---- |
| 1 | 練習用脆弱アプリ（第一候補: **VAmPI** / Flask 製の脆弱 API） | 主ターゲット | 脆弱性が公開されており、**正解と突き合わせて検出精度・誤検知を測れる**。手早く試すなら DSVW（単一ファイル）も候補 |
| 2 | ローカルで起動した **couple-gifted**（Rails API） | 任意の第2ターゲット | 「作りかけの実アプリに向けるとどうか」という現実的な素材。**自分のローカルインスタンスのみ** |

- 練習用アプリは、着手前に「現在もメンテされているか・Docker で簡単に立つか」を確認して確定する。
- 接続先はすべて `localhost`。外部に出ない構成にする。

## ツール

- RedAmon（本家: https://github.com/samugit83/redamon 、MIT）。フォークではなく本家を使い、**動かす前に中身を確認**する。
- 構成・起動方法・対応 LLM・必要スペックは**リポジトリの README で確認**してから着手（Docker Compose で複数のセキュリティツール＋ AI エージェントを立てる構成。詳細は README を正とする）。

## 手順（フェーズ）

| フェーズ | 内容 |
| -------- | ---- |
| 0. 準備 | Anthropic Console で API キー発行＋**月の利用上限を設定（例 $10）**。安い `claude-haiku-5-5` から試す。RedAmon の対応 LLM を README で確認 |
| 1. 練習アプリ起動 | 練習用脆弱アプリをローカル Docker で起動し、既知の脆弱性一覧（正解）を手元に用意 |
| 2. RedAmon 起動 | 本家を clone →中身確認→ README どおり起動。GitHub トークンは最小権限 |
| 3. 実行① | 練習アプリだけに向けて実行。偵察→検出→（任意で）修正 PR 生成までの流れを一周 |
| 4. 評価 | 下の記録テンプレートに沿って観点を記録。検出結果を「正解」と突き合わせる |
| 5. 実行②（任意） | ローカル couple-gifted を対象に同じ流れを実行し、現実的なアプリでの所感を追記 |
| 6. まとめ | 現場共有用のまとめ＋ Qiita 下書き |

## 記録テンプレート（現場共有のため）

| 観点 | 記録すること |
| --- | --- |
| 導入コスト | 起動までの時間・手順のつまずき・必要スペック（CPU/メモリ） |
| 使い勝手 | 対象の指定方法・UI/CLI の分かりやすさ・人の承認ゲートの挙動 |
| 検出精度 | 既知脆弱性をどれだけ拾えたか（検出率）・**誤検知の数**（正解と突合） |
| 自動修正 PR | 生成された修正 PR の妥当性・そのまま使えるか |
| コスト | 実際にかかった API 料金・1 回の実行時間 |
| CI 適合性 | 定期実行・CI 組み込みに向くか |
| 安全面 | ガードレールの効き方・実運用時に必要な許可/スコープ/トークン権限 |
| 総評 | 現場の QA に取り込む価値・導入条件・次アクション |

## やらないこと

- 実システム（勤務先・他社・ホスティング上）への攻撃。
- 外部サービス（メール送信・外部 API 等）に実際に到達する操作。
- promptfoo の検証（別計画 `poc/promptfoo/` で扱う）。
